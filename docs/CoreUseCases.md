# Прецеденты ИС «Караваны» — полные описания и диаграммы

Документ содержит полные сценарии всех **34 прецедентов UC-1…UC-34** из [UseCases.md](UseCases.md).
Все общие, тематические и подробные диаграммы собраны в [каталоге диаграмм](diagrams/usecases/README.md).
Архитектурно значимые UC-1, UC-7, UC-16, UC-19 и UC-32 сохранены и отмечены в перечне.
Остальные сценарии детализированы по [SRS.md](SRS.md), [Vision.md](Vision.md) и
[глоссарию](Glossary_Karavany_FNV.md). Описание задаёт целевое поведение продукта и не означает,
что все перечисленные функции уже реализованы.

Для каждого прецедента приведены основной и альтернативные потоки, постусловия, диаграмма
прецедента и диаграмма активности. Оба вида диаграмм доступны в PlantUML и в родном XML
Visual Paradigm. Связи `include` направлены от включающего к включаемому прецеденту, `extend` —
от расширяющего к базовому. Переход между экранами и предварительный вход в систему сами по себе
не создают связей `include` или `extend`.

Общие условия: пользователи действуют в пределах своей организации и полномочий; полный
административный доступ суперпользователя регулируется FR-25. В полевых сценариях отсутствие
связи означает локальное сохранение с ожидающей синхронизацией, а не уже подтверждённое изменение
на сервере. Постусловия относятся к успешному завершению; результат отмены, отказа или локального
сохранения явно указан в соответствующей альтернативе. Сохранение аудита оценивается отдельно
от доступности основных операций. При повторной передаче сначала проверяется идентификатор ранее
принятого события; для дубликата возвращается прежний результат до повторной проверки порядка
этапов и статуса, которые могли измениться после первой обработки.

Номер альтернативы обозначает шаг основного потока, в котором возникает ответвление; после
стрелки указан возврат, продолжение или конечный результат. В диаграммах активности сохранены
все перечисленные основные шаги и альтернативы. UC-14, UC-17 и UC-18 уточняют обработку того же
события UC-16: общие действия фиксации, проверки и сохранения выполняются один раз, а описания
расширений раскрывают их для соответствующего вида события; второе независимое событие не создаётся.

## UC-1. Создать заявку на перевозку

| Прецедент: Создать заявку на перевозку |
| :--- |
| **ID:** UC-1 |
| **Краткое описание:** Диспетчер создаёт новую заявку на перевозку, выбирая шаблон маршрута или заполняя данные вручную. |
| **Главные актёры:** Диспетчер караванов |
| **Второстепенные актёры:** Wasteland Intel (для расчёта risk_score) |
| **Предусловия:** <br>1. Диспетчер аутентифицирован и действует в рамках своей организации.<br>2. Создаётся новая заявка; доступен шаблон маршрута либо данные для ручного планирования. |
| **Основной поток:** <br>1. Диспетчер открывает форму создания заявки.<br>2. Диспетчер вводит пункты отправления и назначения, дату отправки и описание груза.<br>3. Диспетчер указывает оценочную ценность груза в крышках (UC-12).<br>4. Диспетчер выбирает шаблон или формирует маршрут через UC-5.<br>5. Система получает данные об угрозах и рассчитывает risk_score с учётом ценности груза (UC-7).<br>6. Система рассчитывает ETA по выбранному маршруту (UC-6).<br>7. Система показывает результат UC-8: при рассчитанном риске — рекомендацию по охране и припасам, уже полученную в UC-7; при «Н/Д» — отсутствие достоверной рекомендации.<br>8. Диспетчер проверяет сводку и подтверждает создание; система проверяет обязательные поля.<br>9. Система сохраняет заявку со статусом Draft, начальную запись истории и событие создания в журнале аудита. |
| **Альтернативные потоки:** <br>4а. Вместо шаблона диспетчер задаёт контрольные точки вручную; UC-5 проверяет маршрут → переход к шагу 5.<br>5а. Wasteland Intel недоступен или ответ непригоден — UC-7 возвращает «Н/Д, требует пересчёта»; достоверная рекомендация по риску не формируется → переход к шагу 6.<br>5б. Данные об угрозах старше 24 часов — риск рассчитывается с пометкой об устаревших данных → переход к шагу 6.<br>8а. Диспетчер отменяет создание → завершение без сохранения заявки.<br>8б. Обязательные поля заполнены неверно — система показывает ошибки → возврат к шагу 2. |
| **Постусловия:** <br>1. В организации создана заявка со статусом Draft, маршрутом, ценностью груза и ETA.<br>2. Риск и рекомендация сохранены вместе с признаком актуальности; при недоступном источнике явно показано, что риск требует пересчёта.<br>3. Создание заявки отражено в истории и аудите. |
| **Включаемые прецеденты:** UC-5, UC-6, UC-7, UC-8, UC-12. |

## UC-2. Управлять статусами заявки

| Прецедент: Управлять статусами заявки |
| :--- |
| **ID:** UC-2 |
| **Краткое описание:** Система поддерживает статусную модель заявки (Draft, Ready, En Route, Delayed, Delivered, Closed, Cancelled), переходы инициируются пользователями или событиями. |
| **Главные актёры:** Диспетчер караванов, Караван-мастер |
| **Второстепенные актёры:** Нет |
| **Предусловия:** <br>1. Ручной переход инициирует аутентифицированный пользователь своей организации; автоматический переход запускается зарегистрированным событием этой организации.<br>2. Заявка существует; текущий статус доступен для просмотра. Возможность перехода проверяется в ходе сценария. |
| **Основной поток:** <br>1. Пользователь открывает карточку заявки и видит её текущий статус.<br>2. Система показывает переходы, доступные из текущего статуса, с указанием ролей, которым они разрешены.<br>3. Пользователь выбирает переход (например, «Караван вышел на маршрут») и при необходимости указывает причину.<br>4. Система проверяет допустимость перехода по статусной модели.<br>5. Система проверяет права роли пользователя на этот переход.<br>6. Система проверяет обязательную причину и готовность данных для целевого статуса (FR-10: перевод в «В пути» блокируется при незаполненных обязательных ролях команды).<br>7. Система изменяет статус заявки.<br>8. Система добавляет запись в историю изменений статуса: исходный и целевой статус, роль и имя актора, причина, отметка времени.<br>9. Система записывает событие изменения статуса в журнал аудита. |
| **Альтернативные потоки:** <br>2а. Заявка в финальном статусе Closed или Cancelled — система показывает историю без переходов → завершение без изменения статуса.<br>4а. Переход не предусмотрен моделью — система сообщает допустимые действия → возврат к шагу 2.<br>5а. Роль не имеет права выполнить переход — система отклоняет действие → возврат к шагу 2.<br>6а. Не заполнены обязательные роли или другие предусмотренные для целевого статуса данные — система перечисляет причины → возврат к шагу 2.<br>6б. Для задержки не указана обязательная причина — система запрашивает её → возврат к шагу 3.<br>7а. Переход инициирован зарегистрированным событием UC-19, а не человеком; система выполняет проверки шагов 4–6, изменяет статус и задаёт актора «Система» → переход к шагу 8. |
| **Постусловия:** <br>1. Заявка находится в новом статусе.<br>2. В истории изменений статуса зафиксирован переход с автором, временем и причиной.<br>3. В журнале аудита зафиксировано событие изменения статуса. |

## UC-3. Просмотреть реестр рейсов

| Прецедент: Просмотреть реестр рейсов |
| :--- |
| **ID:** UC-3 |
| **Краткое описание:** Диспетчер просматривает дашборд активных рейсов с цветовой индикацией статуса и risk_score. |
| **Главные актёры:** Диспетчер караванов |
| **Второстепенные актёры:** Нет |
| **Предусловия:** <br>1. Диспетчер аутентифицирован и действует в рамках своей организации.<br>2. Разрешён просмотр реестра организации; отсутствие заявок допускается. |
| **Основной поток:** <br>1. Диспетчер открывает реестр рейсов.<br>2. Система определяет организацию диспетчера и отбирает рейсы только этой организации.<br>3. Система показывает срез активных рейсов: маршрут, пункты отправления и назначения, дата отправки, описание и ценность груза, ETA, статус, risk_score с рекомендацией, последнее изменение статуса.<br>4. Система отмечает статус цветным бейджем, а risk_score — цветным уровнем риска; цвет всегда сопровождается текстовой подписью.<br>5. Система выделяет рейсы, требующие внимания, и указывает причину.<br>6. Система показывает сводку по срезу: число рейсов, распределение по статусам, распределение по уровням риска и число рейсов, требующих внимания.<br>7. Диспетчер отбирает рейсы фильтрами (статус, уровень риска, только требующие внимания) и выбирает порядок сортировки.<br>8. Система применяет отбор и сортировку, сохраняя ограничение организацией; сводка при этом не меняется.<br>9. Диспетчер переключается на срез завершённых рейсов или открывает карточку рейса, откуда доступны управление статусом и история переходов (UC-2) и разбор расчёта risk_score (UC-7). |
| **Альтернативные потоки:** <br>1а. Организация не выбрана — система показывает доступные организации и не раскрывает рейсы до выбора разрешённого контекста → возврат к шагу 1 после выбора организации.<br>3а. В организации нет заявок — система показывает пустой реестр с предложением создать заявку через UC-1 → завершение просмотра пустого реестра.<br>3б. Сервер недоступен — система сообщает об ошибке и не показывает частичных данных; диспетчер повторяет загрузку → возврат к шагу 1.<br>5а. risk_score не рассчитан (UC-7, альт. 2а) — значение показано как «Н/Д» нейтральным цветом с пометкой «требует пересчёта»; диспетчер при необходимости запускает UC-7 → переход к шагу 6 после показа результата либо причины недоступности.<br>5б. risk_score рассчитан по данным старше 24 часов (UC-7, альт. 2б) — уровень риска сохраняется с пометкой об устаревших данных → переход к шагу 6.<br>8а. Под фильтры не подошёл ни один рейс — система показывает пустой результат, сводка по срезу сохраняется; диспетчер меняет либо сбрасывает фильтры → возврат к шагу 7.<br>9а. Рейс находится в финальном статусе — карточка открывается только для просмотра, переходов нет (UC-2, альт. 2а) → завершение просмотра карточки.<br>9б. Нужен разбор истории завершённых рейсов — реестр переключается на архивный срез; дальнейшие поиск и фильтрация выполняются в UC-4 (FR-4) → завершение просмотра активного среза. |
| **Постусловия:** <br>1. Диспетчеру показан реестр рейсов его организации; рейсы других организаций не показаны ни при каких фильтрах.<br>2. Активные и завершённые рейсы разделены на срезы, по умолчанию открыт срез активных.<br>3. У каждого рейса есть цветовая индикация статуса и уровня риска с текстовой подписью, включая «Н/Д» и пометку об устаревших данных.<br>4. Отбор и сортировка применены; данные системы запросом реестра не изменены. |

## UC-4. Поиск и фильтрация завершённых рейсов

| Прецедент: Поиск и фильтрация завершённых рейсов |
| :--- |

Система проверяет параметры, сохраняет новое состояние подписки и фиксирует изменение в аудите.<br>6. Система применяет доступ организации в соответствии с новым состоянием и показывает результат. |
| **Альтернативные потоки:** <br>1б. Наступил срок истечения подписки — сценарий запускается автоматически без ручного изменения; система фиксирует истечение, применяет предусмотренный политикой лицензирования режим доступа и записывает событие в аудит → завершение с состоянием истёкшей подписки и доступом по политике лицензирования.<br>4а. Суперпользователь отменяет действие → завершение с прежней подпиской.<br>5а. Параметры некорректны — система поясняет ошибку → возврат к шагу 4. |
| **Постусловия:** <br>1. Уровень, срок и состояние подписки отражают выполненное действие.<br>2. Права доступа соответствуют подписке; данные организации не удалены изменением подписки. |
| **Расширяемый прецедент:** UC-32, EP-2 «Управление подпиской», по выбору суперпользователя; остальные операции подписки запускаются самостоятельно. |
