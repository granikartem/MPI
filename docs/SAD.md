# Software Architecture Document - ИС «Караваны»

Описание архитектуры. Структура разделов - по шаблону дисциплины. Рабочий индекс исходников
диаграмм с краткими описаниями каждой - [SAD_Diagrams.md](SAD_Diagrams.md).

## 1. Introduction (Введение)

### 1.1 Purpose (Назначение)

Документ описывает архитектуру ИС «Караваны»: принятые проектные решения и представления архитектуры
по модели 4+1 - Use-Case View, Logical View, Process View, Deployment View и Implementation View
(разделы 4–8). Он служит основанием для реализации, тестирования и сопровождения системы и фиксирует,
какими средствами выполняются требования [SRS](SRS.md).

### 1.2 Scope (Область применения)

Документ охватывает всю систему: web-клиент диспетчера и суперпользователя, полевой клиент
Pip-Boy, серверную часть, хранилища PostgreSQL и MongoDB, интеграции
с внешними системами Wasteland Intel и NCR Checkpoint & Tax Terminal, а также развёртывание на
центральном сервере под FreeBSD.

Каждая точка зрения охватывает систему целиком, но с разной глубиной:

- **Use-Case View** - предметная область: акторы, границы системы и поведение прецедентов, без
  привязки к реализации;
- **Logical View** - слои, логические компоненты и правила зависимостей между ними;
- **Implementation View** - фактический код: классы и их методы, эндпоинты, модель базы данных;
- **Process View** - процессы, привязанные к моментам времени;
- **Deployment View** - размещение компонентов по машинам, протоколы и порты.

## 3. Architectural Goals and Constraints (Цели и ограничения архитектуры)

Раздел собирает требования и условия, которые определили структуру системы: что архитектура обязана
обеспечить, чем она ограничена и какие отступления от ограничений зафиксированы на сегодня.
Значения показателей и способы их проверки не дублируются здесь — они в разделах
[9](#9-size-and-performance-производительность) и [10](#10-quality-качество).

### 3.2 Ограничения, заданные требованиями

| Ограничение | Требование | Архитектурное следствие |
|---|---|---|
| Клиент-серверная архитектура | DC-1 | Вся логика прецедентов — на сервере; клиенты обращаются только к REST-контракту и собственной логики принятия решений не содержат |
| Web-клиент на React 18 | DC-2, DC-7 | Разделение на страницы, презентационные компоненты и сервисный слой HTTP-клиента; состояние живёт в контейнерах страниц |
| Серверная часть на Java 21 | DC-3 | Spring Boot, доступ к оперативному хранилищу через JPA, версионирование схемы миграциями |
| Оперативные данные и пользователи — PostgreSQL 16 | DC-4 | Заявки, маршруты, участки, контрольные точки, организации, учётные записи и история статусов хранятся реляционно |
| События — MongoDB 7 | DC-5 | Снимки оценки риска и журнал аудита хранятся документами: состав полей снимка меняется вместе с формулой, схема заранее не фиксируется |
| Layered: Controller → Service → Repository | DC-6 | Слои `presentation` → `application` → `domain` с доступом `application` → `infrastructure`; обращения только сверху вниз |
| Готовая UI-библиотека и библиотека графиков | DC-8 | Экраны диспетчера и отчёты собираются из готовых компонентов и графиков; собственные компоненты допускаются только при отсутствии подходящего аналога |
| Отклик не более 1 секунды | PF-4 | Реестр рейсов читается одним запросом с ограничением выдачи; тяжёлые обращения к внешней разведке вынесены из чтения реестра в отдельную операцию пересчёта |
| До 200 одновременных пользователей, 500 рейсов и 10 000 событий в день | PF-1 — PF-3 | Один сервер приложений без горизонтального масштабирования; нагрузка удерживается индексами и ограничением выдачи |
| Доступность не менее 99,0 % | RL-2 | Внешние интеграции не критичны для основного потока: их отказ деградирует функцию, но не сервис |
| Проприетарная лицензия, подписка | SRS 3.7, Vision 4.4 | Уровень подписки — свойство организации; по истечении оплаченного периода доступ ограничивается чтением на 30 дней grace-периода |

### 3.3 Ограничения окружения и эксплуатации

- **Один центральный сервер** (16 ядер Intel Xeon E5-2643, 128 ГБ, 26 ТБ) под FreeBSD 14.3-STABLE
  ([Vision](Vision.md), раздел 9.2). Резервирования сервера нет, отказоустойчивость обеспечивается
  резервным копированием, а не кластером.
- **Все серверные компоненты ставятся из пакетов FreeBSD и работают как службы rc.d**, контейнеров
  в целевой эксплуатации нет. Backend и базы данных слушают только петлевой интерфейс, наружу
  сетевой фильтр пропускает единственный порт HTTPS.
- **Резервные копии выгружаются на голотейп** — носитель, доступный в предметной области;
  восстановление ручное.
- **Терминал активируется API-ключом** с сроком действия, равным оплаченному периоду подписки
  ([Vision](Vision.md), раздел 9.4); архитектура должна допускать выпуск нового ключа без
  переустановки клиента.

### 3.4 Безопасность, разграничение доступа и приватность

- **Граница изоляции — организация.** Данные рейсов и учётные записи принадлежат организации;
  запросы к реестру и заявкам выполняются в её пространстве (FR-23, FR-24).
- **Ролевая модель.** Диспетчер, кладовщик, караван-мастер, капитан охраны и медик видят разные
  наборы данных; сведения о спецгрузах, составе груза, медицинских обстоятельствах и угрозах
  не должны быть доступны всем ролям одинаково (SRS 2.4).
- **Пароли не хранятся в открытом виде** — только необратимый хеш.
- **Журнал аудита** фиксирует автора, время и содержание изменения и хранится не менее 3 месяцев
  (RL-4, RL-5).

## 9. Size and Performance (Производительность)

Требования к производительности заданы в [SRS](SRS.md) (PF-1…PF-4, RL-1, RL-3, RL-5) и в
[Vision](Vision.md), разделы 7 и 9. Ниже - архитектурные решения, которые их обеспечивают.

| Решение | Суть решения |
|---|---|
| Сервер без состояния | Приложение не хранит данные пользователя между запросами: личность подтверждается токеном, данные лежат в БД. Любой экземпляр обработает любой запрос, поэтому нагрузка масштабируется добавлением экземпляров за балансировщиком |
| Разделение хранилищ по типу данных | PostgreSQL - оперативные данные с транзакциями (заявки, маршруты, организации, пользователи, история статусов). MongoDB - дописываемые данные (полевые события, снимки расчета риска, журнал аудита). Основной поток записи (PF-3) не мешает транзакциям по заявкам |
| Итоги расчета хранятся в заявке | risk_score, признак актуальности, рекомендация и ETA записаны в самой заявке. Реестр и карточка рейса читаются без обращения к MongoDB и внешним системам. Подробный снимок расчета загружается отдельно, только когда диспетчер его открывает |
| Короткие транзакции | Транзакция охватывает только запись заявки и истории статусов в PostgreSQL. Запрос к внешней системе выполняется до нее, запись в журнал аудита MongoDB - после. Соединение с БД занято только на время записи, поэтому небольшого пула соединений хватает на всю нагрузку |
| Вызов внешних систем | Wasteland Intel и NCR Checkpoint & Tax Terminal вызываются с ограниченным временем ожидания, чтобы создание заявки укладывалось в 1 секунду (PF-4). Нет ответа - заявка все равно создается, risk_score получает состояние «Н/Д, требует пересчета» и рассчитывается позже по действию диспетчера. Полученный ответ хранится с датой актуальности и годен 24 часа: внешняя система опрашивается при создании заявки и пересчете, но не при чтении |
| Полевой клиент: очередь и пакетная передача | Событие фиксируется в локальном хранилище Pip-Boy, ввод не ждет сервер. При появлении связи очередь уходит одним запросом и записывается в MongoDB одной операцией, поэтому после массового восстановления связи число запросов пропорционально числу устройств, а не событий (RL-1, RL-3). Оболочка приложения хранится на устройстве, по каналу передаются только данные |
| Прием событий без дублей | Идентификатор события создается на устройстве, в хранилище на нем уникальный индекс. Повторная отправка после обрыва связи безопасна: дубль не появится, а серверу не нужно подтверждать и сверять каждое событие |
| Автоочистка журнала аудита | Записи удаляются самой MongoDB по истечении срока хранения (не менее 3 месяцев, RL-5). Приложение пакетную очистку не выполняет, объем журнала перестает расти |
