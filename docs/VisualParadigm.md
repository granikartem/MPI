# Перенос диаграмм SAD из PlantUML в Visual Paradigm

Инструкция описывает, как получить диаграммы комплекта SAD в родном формате Visual Paradigm
**без единого действия мышью**: исходник собирается как XML, импортируется консольной утилитой
и выгружается в PNG. Всё описанное ниже проверено запуском на Visual Paradigm **Community
Edition 18.1** — утверждения вида «должно работать по документации» в инструкцию не включались.

Рабочие примеры лежат в [`diagrams/vp/examples`](diagrams/vp/examples): по одному на каждый тип
диаграммы, каждый импортируется и отрисовывается.

## 1. Что потребуется один раз

**Дистрибутив.** Портативная сборка (InstallFree), инсталлятор и права администратора не нужны:
`https://www.visual-paradigm.com/download/community.jsp?platform=windows&arch=64bit&install=no`
Архив `Visual_Paradigm_CE_Win64_InstallFree.zip`, ~815 МиБ. Распаковать вне репозитория, например
в `C:\Users\<логин>\tools\`. После распаковки — 1.1 ГБ, внутри собственная JRE 11.

**Активация.** Community Edition не работает без лицензии: любая утилита отвечает
`License not found`. Нужно один раз запустить `Visual Paradigm.exe`, выбрать Community Edition,
указать почту и принять условия некоммерческого использования. Это единственный шаг, требующий
графического интерфейса. Дальше GUI не нужен.

**Каталог настроек.** Если `%APPDATA%\VisualParadigm` отсутствует, первый запуск падает с
`java.io.IOException`. Создать заранее.

Далее по тексту `$VP` — корень распакованной сборки,
например `C:\Users\a.granik\tools\Visual Paradigm CE 18.1`.

## 2. Что доступно в Community Edition

Проверено перебором всех консольных утилит из `$VP\Application\scripts`.

| Утилита | CE | Назначение |
|---|---|---|
| `ImportXML` | **работает** | собрать проект из XML |
| `ExportXML` | **работает** | выгрузить проект обратно в XML — главный инструмент отладки |
| `ExportDiagramImage` | **работает** | PNG, JPG, SVG, PDF |
| `ImportXMI`, `ExportXMI` | заблокировано | — |
| `InstantReverse` | заблокировано | обратная разработка по исходникам Java |

Отсюда два следствия. Первое: обмен через XMI невозможен, работаем только с **родным XML-форматом
проекта** — что лучше, потому что он описывает и модель, и холст с раскладкой. Второе: диаграмму
классов нельзя получить автоматически из кода, её нужно собирать самостоятельно.

**Водяной знак.** Community Edition печатает в правом нижнем углу каждой выгруженной картинки
однострочную подпись «Powered By Visual Paradigm Community Edition». Убрать нельзя.

## 3. Конвейер

```
модель диаграммы  →  project.xml  →  ImportXML  →  .vpp  →  ExportDiagramImage  →  .png
```

PlantUML остаётся источником содержания: из `.puml` берутся элементы, связи, подписи и заметки.
Автоматического преобразования `.puml → XML` нет и быть не может — координаты каждого элемента
в PlantUML не заданы, их вычисляет Graphviz/smetana при рендеринге. В Visual Paradigm раскладку
задаёт автор файла (см. раздел 8).

## 4. Команды

Все пути — абсолютные. Скрипты выполняют `pushd ..\bin`, поэтому запускать их можно **только**
из каталога `scripts`.

```powershell
$env:HEADLESS = "true"
Set-Location "$VP\Application\scripts"

# XML -> проект
cmd /c ".\ImportXML.bat -project `"<ABS>\out.vpp`" -file `"<ABS>\diagram.xml`""

# проект -> картинки (-diagram обязателен; формат задаётся -type, НЕ -format)
cmd /c ".\ExportDiagramImage.bat -project `"<ABS>\out.vpp`" -out `"<ABS>\img`" -diagram `"*`" -type png_with_background"

# проект -> XML (отладка: видно, как VP понял наш файл)
cmd /c ".\ExportXML.bat -project `"<ABS>\out.vpp`" -out `"<ABS>\xml`" -noimage"
```

PNG получает имя из атрибута `name` элемента `<Diagram>`.

**Тип `png_with_background`, а не `png`.** Обычный `png` выгружается с альфа-каналом: всё, что
не занято фигурами, прозрачно. В просмотрщике с тёмной темой и при обрезке такая картинка выходит
чёрной. Для вставки в документ нужен непрозрачный фон.

Два правила, без которых отладка превращается в гадание:

- **`ImportXML` дописывает в существующий `.vpp`.** Перед чистым прогоном удалять `out.vpp`
  и `out.vpp.bak_*`, иначе в проекте появятся дубли диаграмм.
- **`ExportDiagramImage` не перезаписывает существующий каталог `-out`**, а кладёт рядом файл
  с суффиксом «2». Легко несколько итераций подряд смотреть на устаревшую картинку. Каждый прогон —
  в новый каталог.

## 5. Обязательная процедура проверки

Это не формальность: половина ошибок формата проявляется именно так.

1. **Проверить вывод импорта на исключения.** `ImportXML` может напечатать
   `java.lang.NullPointerException`, а следом — `Saved project`. Проект сохранится, но часть
   моделей в него не попадёт: классы останутся без типов и стереотипов, связи пропадут целиком.
   Смотреть на исключения, а не на слово `Saved`.

   Фильтровать нужно по `java\.lang\.`, `java\.io\.` или `^\s+at v\.` — **не по слову
   `Exception`**: PowerShell оборачивает любой вывод `.bat` в собственную диагностику со словом
   `RemoteException`, и поиск по подстроке `Exception` даёт ложное срабатывание на каждом
   успешном прогоне.
2. **Открыть полученный PNG и посмотреть на него.** Единственный надёжный критерий. Наличие
   константы в `openapi.jar` не означает, что `ImportXML` это нарисует: типы `ObjectFlow`
   и `ActivityObject` в библиотеке есть, а на картинке не появляются.
3. При расхождениях — `ExportXML` обратно и сравнить с тем, что отправляли.

## 6. Формат: общие правила

```xml
<?xml version="1.0" encoding="UTF-8"?>
<Project xmlns="http://www.visual-paradigm.com/product/vpuml/modelexporter"
         name="..." umlVersion="2.x" exporterVersion="18.1">
  <Models>   <!-- элементы модели --> </Models>
  <Diagrams>
    <Diagram id="................" name="Имя диаграммы" diagramType="ClassDiagram">
      <Shapes/>
      <Connectors/>
    </Diagram>
  </Diagrams>
</Project>
```

`diagramType`: `ClassDiagram`, `ActivityDiagram`, `UseCaseDiagram`.

**Идентификаторы — ровно 16 символов** из `[\w\d_.]` (`project.xsd`, `simpleType modelId`,
`minLength = maxLength = 16`). Другая длина ломает импорт тихо. **И только ASCII:** проверку
выполняет java-регексп, где `\w` кириллицу не пропускает, поэтому id вроде `S_cmp_внешняяс00`
Visual Paradigm молча перевыпускает — а ссылки на него (`verticalPartitionId`, `compartmentIds`
и прочие) остаются старыми, и связанные фигуры пропадают с картинки. Удобно писать осмысленные имена
в шаблоне и добивать нулями генератором:

```python
def mid(s):
    r = s + "0" * (16 - len(s))
    assert re.fullmatch(r"[\w\d_.]{16}", r)
    return r
```

**Модель и представление разделены.** `<Model>` живёт в `<Models>`, `<Shape>` и `<Connector>` —
внутри `<Diagram>`; связывает их атрибут `model="<id модели>"`. Легко перепутать: у `<Model>`
связи атрибуты `from`/`to` содержат **id моделей**, у `<Connector>` — **id фигур**.

**Подпись не появится сама.** Чтобы текст был виден, нужны три вещи одновременно: атрибут `name`
у `<Model>`, свойство `<StringProperty name="name" value="..."/>` внутри `<ModelProperties>`
и дочерний `<Caption visible="true" .../>` у фигуры. Без `Caption` фигура рисуется пустой.
То же касается коннекторов: связь с заданным именем, но без `Caption`, выйдет без подписи.

- `Caption` у **фигуры** — координаты относительные: всегда `x="0" y="0"`, `width`/`height` равны
  размеру фигуры.
- `Caption` у **коннектора** — координаты абсолютные, в системе холста. С нулями все подписи
  соберутся в левом верхнем углу.
- `width` задаёт обрезку: при `width="0"` текст не виден вовсе, при малом — обрезается многоточием.

**Порядок дочерних элементов фиксирован схемой** и его нарушение делает файл невалидным:
`DiagramElementProperties → ElementFont → Line → Caption → Icons → ChildShapes → FillColor`,
у коннектора далее `RoleA → RoleB → Points`.

**Многострочный текст** — только символьная ссылка `&#10;` внутри значения атрибута. Литеральный
перевод строки XML-парсер схлопнет в пробел.

**Кириллица** работает везде без исключений — имена классов, стереотипов, атрибутов, операций,
параметров, ролей, кратностей, пакетов, подписи связей, текст заметок, включая «ё», кавычки-ёлочки
и длинное тире. Файл писать в UTF-8 с объявлением кодировки.

**Цвет заливки** — последний дочерний элемент фигуры:
`<FillColor type="1" color="Cr:R,G,B,A" transparency="0" style="0"/>`.

**Заголовка у диаграммы нет.** В Visual Paradigm нет свойства «заголовок», аналогичного `title`
в PlantUML. Крупную надпись приходится имитировать фигурой: подходит только `OpaqueAction`
с заданным `name` и крупным полужирным `<ElementFont>` — заметка `NOTE` игнорирует заданный ей
шрифт и рисуется мелким, `GenericShape` с `customText` не рисуется вовсе, `DiagramInfo` даёт
пустую рамку. Побочный эффект: в модели остаётся лишнее действие. Если заголовок не обязателен,
проще обойтись именем диаграммы — оно попадает в имя PNG.

**Заметка** — `modelType` и `shapeType` строго заглавными: `NOTE`. Текст берётся **только** из
`<HTMLProperty name="documentation" plainTextValue="строка1&#10;строка2"/>`; `name`, `customText`
и `description` игнорируются. `Caption` заметке не нужен. Пунктирная привязка — коннектор
`Anchor`, которому обязательна парная модель с `from`/`to`.

## 7. Рецепты по типам диаграмм

Полные рабочие файлы — в [`diagrams/vp/examples`](diagrams/vp/examples). Ниже только то,
что неочевидно и на чём легко потерять время.

### 7.1 Диаграмма классов — `examples/class.xml`

Работает: стереотипы, абстрактный класс курсивом, статические члены подчёркиванием, кратности
и роли на обоих концах, композиция и агрегация, обобщение, реализация, зависимости, заметки
с привязкой, пакеты, перечисления.

- **Интерфейса нет.** `<Model modelType="Interface">` с любыми дочерними элементами роняет импорт
  в `NullPointerException`; `shapeType="Interface"` не рисуется; фигура `Class` на модели
  `Interface` роняет экспорт картинки в `ClassCastException`. Интерфейс делается как
  `modelType="Class"` со стереотипом `interface`.
- **Перечисления нет.** Отдельного `modelType` для enum не существует. Enum — это `Class`
  со стереотипом `enumeration` и дочерними `EnumerationLiteral`.
- **Тип атрибута** задаётся только через `<TextModelProperty name="type">` с вложенным
  `<ModelRef/>` или `<StringValue/>`. `<StringProperty name="type">` молча игнорируется.
  У операции то же свойство называется `returnType`.
- **Точка внутри типа обрезает текст.** Значение `type`/`returnType` VP разбирает как полное имя
  и рисует только часть после последней точки: `double = 4.0` превращается в `0`,
  `String {альт. поток 3а}` — в ` поток 3а}`, `RequestRegistry.Summary` — в `Summary`.
  Лечится заменой точки на `U+2024` (ONE DOT LEADER) внутри значения типа — на картинке
  неотличимо. В **именах** класса, поля и операции точка безопасна.
- **Порядок членов задаёт VP, а не файл.** Сначала рисуется весь отсек атрибутов, затем весь
  отсек операций. Если в исходнике после сигнатур снова идёт строка-пояснение
  (`.. плюс геттеры всех полей ..`), она уедет вверх. Чтобы сохранить порядок строк оригинала,
  такой класс собирается «плоско»: каждая строка — атрибут с готовым текстом, видимость
  подставляет сам VP. То же касается `EnumerationLiteral` — литералы рисуются после методов.
- **Композиция и агрегация** — это обычная `Association`, различие только в
  `<StringProperty name="aggregationKind">` у нужного конца: `None`, `Aggregation`, `Composited`.
  Свойство конца связи называется `EndModelElement`, с заглавной «E».
- **Направление стрелки задаёт `Connector`, а не модель.** У `Generalization` и `Realization`
  треугольник ставится на конце `from`, у `Dependency` стрелка — на конце `to`. Поэтому для
  наследования и реализации коннектор пишется «задом наперёд»: `from` — предок или интерфейс.
- **Элемент `<Line>` на фигуре непригоден**: с `transparency="0"` он убирает рамку, без него
  импорт падает на диапазоне альфа-канала. Не использовать.
- **`<Line>` у коннектора читается, но не рисуется.** Схема допускает `<Line cap="0" weight="…"><Stroke><Dashes><Dash value="5"/>…`, и без атрибута `cap`
  импорт падает с `IllegalArgumentException: illegal end cap value` — то есть элемент разбирается. Но ни пунктир, ни толщина на картинке не появляются (проверено замером
  пикселей: линия остаётся сплошной в 1 px). Поэтому **пунктирной ассоциации получить нельзя**: связь PlantUML `..` между классами переносится сплошной `Association`.
  Побочный эффект: лишний `<Line>` раздувает рассчитанные границы холста — PNG вырастает на несколько десятков пикселей.
- **Стрелка навигации у ассоциации требует двух вещей сразу:** `<IntegerProperty name="navigable">` у конца (`IAssociationEnd`: 0 — navigable, 1 — unspecified,
  2 — non-navigable) **и** `<IntegerProperty name="showNavigationArrows" value="1"/>` в `DiagramElementProperties` коннектора
  (`IAssociationUIModel.SHOW_NAVIGATION_ARROWS_SHOW_ALL_ARROWS_AND_CROSSES`). Без второго свойства коннектор следует настройке диаграммы и наконечник не рисует —
  отсюда ложный вывод, что `navigable` не работает. Непомеченному концу давать `1`, а не `2`: при `2` VP рисует на нём крестик.
- Абстрактный класс или операция — `<BooleanProperty name="abstract" value="true"/>`;
  статический член — `<StringProperty name="scope" value="classifier"/>`.

### 7.2 Диаграмма активности с дорожками — `examples/activity-swimlanes.xml`

Дорожки работают, вертикальные и горизонтальные.

Узлы (`modelType` совпадает с `shapeType`): `InitialNode`, `ActivityFinalNode`, `FlowFinalNode`,
`ActivityAction`, `DecisionNode`, `MergeNode`, `ForkNode`, `JoinNode`, `ObjectNode`,
`DataStoreNode`, `CentralBufferNode`, `SendSignalAction`, `AcceptEventAction`.
Связи: `ControlFlow`, `ActivityObjectFlow`, `Anchor`.

- **Дорожки — это один контейнер с четырьмя детьми на две дорожки.** Модель: один
  `ActivitySwimlane2`, внутри которого партиции вложены как `<Model>` в
  `<ModelsProperty name="verticalPartitions">` — не через `ChildModels` и не ссылками.
  Фигура: `ActivitySwimlane2` с дочерними `ActivityPartitionHeader` (заголовок) и
  `ActivitySwimlane2Compartment` (отсек) на каждую дорожку.
- **В `verticalPartitionIds` и `verticalPartitionId` лежат id фигур-заголовков, а не id моделей
  партиций.** Самая частая ошибка.
- **Узел попадает в дорожку только по координатам.** Узлы остаются фигурами верхнего уровня
  в `<Shapes>`, внутрь отсека их класть не нужно; свойство `containedElements` у партиции
  не требуется. Координаты дочерних фигур контейнера — абсолютные, как у родителя.
- **Горизонтальные дорожки** требуют всех четырёх изменений сразу: `horizontalPartitions`,
  `horizontalPartitionIds`, `horizontalPartitionId` и `horizontal="true"` у заголовка.
  Геометрия зеркальная: заголовки — узкой колонкой слева шириной 30, отсеки сдвинуты вправо.
  Текст заголовка VP поворачивает сам.
- **Вопрос развилки помещается в ромб, но только если ромб достаточно велик.** При размере
  40×40 собственный `Caption` узла `DecisionNode` обрезается до невидимого, и текст вопроса
  пропадает молча — узел выглядит пустым ромбом. Примерно с 300×60 вопрос рисуется внутри,
  как `if (вопрос?)` в PlantUML. Это самая дорогая из найденных ловушек: содержание теряется,
  а картинка выглядит правдоподобно.
- **Подпись ветвления**: `<StringProperty name="guard" value="да"/>` рисуется в квадратных
  скобках, `name` — как есть; заданные одновременно дают две строки.
- **Полужирный заголовок дорожки** — `<ElementFont name="Dialog" color="Cr:0,0,0,255" size="11"
  style="1"/>` вторым дочерним элементом фигуры-заголовка, сразу после
  `DiagramElementProperties`. Соответствует `skinparam swimlaneTitleFontStyle bold`.
- **Узлы слияния по умолчанию ярко-голубые.** Если остальные узлы серые, `MergeNode`
  и `DecisionNode` надо красить явно, иначе они выбиваются из палитры.
- **Поток объектов — `ActivityObjectFlow`**, а не `ObjectFlow`: последний есть в библиотеке,
  но молча не рисуется. `ActivityObject` как фигура не рисуется вовсе.
- **Коннектор без атрибута `model` не рисуется.** Каждой связи нужна своя модель с `from`/`to`.
- Привязка заметки к `ObjectNode` не рисуется — цеплять к действию.
- Маршрутизация линий: `connectorStyle="Rectlinear"` даёт автоматическую Г-образную трассу,
  либо задаются явные изломы `<Points>` в абсолютных координатах. Без того и другого — прямая
  наклонная линия. **`<Points>` должны задавать путь целиком**: первая точка — на границе
  фигуры-источника, последняя — на границе фигуры-цели. Неполный список (одна-две точки
  «посередине») молча игнорируется, и линия уходит по автотрассе — часто сквозь соседний блок.
- **Залитый отсек дорожки закрывает узлы, стоящие в ней.** Если `ActivitySwimlane2Compartment`
  получил `FillColor`, узлы этой дорожки на картинке исчезают, хотя в модели они есть и zorder
  у них выше. Лечится вложением: такие узлы кладутся в `ChildShapes` своего отсека
  (`parent=` у фигуры), координаты остаются абсолютными. Вложение в сам `ActivitySwimlane2`
  не помогает. На маленьких диаграммах эффект не воспроизводится — проверять на настоящей.

### 7.3 Диаграмма прецедентов — `examples/usecase.xml`

Работает: акторы, обобщение между акторами и между прецедентами, ассоциации с ролями
и кратностями, граница системы и вложенная граница внутри неё, точки расширения,
`<<include>>` и `<<extend>>` с условием, абстрактный прецедент курсивом.

- **Три связи ведут себя по-разному, запоминать по отдельности.**
  `Include`: `from` — базовый прецедент, `to` — включаемый, стрелка на конце `to`.
  `Extend`: `from` — **базовый** (расширяемый), `to` — расширяющий, стрелка на конце `from`.
  `Generalization`: `from` — родитель, полый треугольник на конце `from`.
- **Отсек `extension points` рисуется у фигуры, стоящей в `from` связи `Extend`.** Если повесить
  точку расширения на один прецедент, а `from` сделать другим, отсек нарисуется не там.
- **`zorder` нельзя чередовать между поддеревьями.** Назначать строго в порядке обхода дерева
  фигур в глубину. При нарушении вложенный контейнер может не отрисоваться целиком — ни рамки,
  ни заголовка, — хотя в проекте он есть.
- **`<Line>` обязан содержать пустой `<Stroke/>`.** Без него экспорт картинки падает на `null
  Stroke`, PNG всё равно создаётся, но часть подписей молча пропадает.
- **Роли и кратности требуют** `requestResetCaption="true"` и `requestResetCaptionSize="true"`.
  При этом свои координаты меток игнорируются — VP расставляет их сам. С `false` для прецедента,
  вложенного в границу системы, они не рисуются вовсе.
- Для группировки внутри границы использовать вложенный `System` или `Package`:
  `modelType="Subsystem"` рисуется как класс с отсеками и не годится.
- `showConnectorName`: `0` — показывать, `1` — прятать, `2` — следовать настройке диаграммы.
  Интуитивное «1» прячет подпись.

## 8. Раскладка

**Автоматической раскладки нет.** Свойство `requestLayoutType` импортируется, но на результат
не влияет; алгоритмы `Organic`, `Hierarchical`, `Orthogonal` в библиотеке есть, но из XML
не запускаются. Координаты и габариты каждого элемента вычисляет автор файла.

Это проверено двумя независимыми путями — и через `ImportXML`, и через Open API, — так что
обходного пути нет. Для диаграмм с дорожками раскладка несложная: номер дорожки задаёт `x`,
порядок шага в потоке — `y`. Для диаграмм классов она требует итераций по картинке.

**Отсюда и берётся конвертер** (§13): раскладку не обязательно придумывать заново — её уже
посчитал PlantUML, и её можно снять с его SVG.

### Порядок наложения: больший `zorder` — дальше от зрителя

Нумерация в порядке создания кажется естественной, но даёт прямо противоположный результат:
контейнер создаётся раньше содержимого, получает меньший номер — и закрашивает собой всё, что
внутри. На картинке вложенных элементов просто нет, хотя `ExportXML` показывает их в проекте
целиком, с верными координатами. Симптом обманчив: выглядит как потеря данных при импорте.

Правило: **крупная фигура получает больший `zorder`, мелкая — меньший.** Достаточно отсортировать
все фигуры диаграммы по убыванию площади и пронумеровать. Это не зависит от того, вложены фигуры
через `ChildShapes` или лежат плоским списком, — порядок наложения решает в обоих случаях.

### `FillColor` ставится последним, а вложение — раньше него

`FillColor` обязан быть последним ребёнком `<Shape>`, а `ChildShapes` добавляется уже после
создания фигуры. Если залить цвет сразу при создании, `ChildShapes` окажется **после**
`FillColor`, и импорт молча потеряет всё вложенное. Поэтому заливка доливается в самом конце,
когда вся вложенность уже построена.

### Маршруты связей

- **`<Points>` задаёт путь целиком или не действует вовсе.** Первая точка — на границе
  фигуры-источника, последняя — на границе цели. Неполный список молча отбрасывается,
  и линия уходит по автотрассе, часто сквозь соседний блок.
- **Двух точек недостаточно** — такой список VP тоже отбрасывает. Минимум три.
- **Точка не должна попадать внутрь своей фигуры.** `y` растёт вниз, поэтому маршрут,
  уходящий вверх от нижней грани источника, легко задаёт первую точку внутри фигуры —
  список отбрасывается молча.
- **Автотрасса не обходит препятствия** и входит в фигуру не по центру грани. Для коротких
  вертикальных связей достаточно одной промежуточной точки на оси, чтобы стрелка встала ровно.
- Выводить ветки развилки лучше из **разных вершин** ромба: одну из нижней, другую из боковой.
  Иначе вход в ромб и выход ветки ложатся на одну горизонталь и сливаются в одну линию.

### Подписи

- **Связь обрезается не о фигуру, а об объединение фигуры и её подписи.** У актора с широкой
  подписью линия, подходящая снизу-слева, обрывается в пустоте за 50–70 px до фигурки.
  Лечится подходом строго горизонтально в полосу самой фигуры.
- **VP рисует подпись связи примерно на 12 px ниже середины ломаной** — при расчёте
  непересечений это смещение надо учитывать.
- Многострочная подпись у связи работает: высота `Caption` 34 вместо 16.
- Длинные подписи (от 45 символов кириллицей) рисуются целиком и не переносятся — налезают
  на соседние фигуры. Разводить фигуры примерно на 500 px, если подпись длинная.
- Ширину `Caption` задавать с запасом, иначе текст обрежется многоточием.
- Координаты в PNG не совпадают с координатами диаграммы: VP нормализует начало координат
  по самому левому и верхнему элементу и добавляет поля. Для сверки положения меток смотреть
  выгрузку `ExportXML`.

### Как проверять раскладку

Глаз пропускает наложения, особенно на больших диаграммах. Дешевле написать геометрическую
проверку по собранному XML: каждый отрезок ломаной против всех прямоугольников, кроме двух своих
концов, плюс поиск почти параллельных отрезков разных связей ближе 12 px и подписей, попавших
на фигуры. Такая проверка на реальных диаграммах нашла наложения, которые не были видны
при просмотре.

## 9. Где искать имена типов

В `project.xsd` имён типов нет — `modelType` объявлен как произвольная непустая строка. Источник
истины — `$VP\Application\lib\openapi.jar`:

```bash
unzip -o "$VP/Application/lib/openapi.jar" -d oapi
javap -constants -cp oapi com.vp.plugin.model.factory.IModelElementFactory
javap -constants -cp oapi com.vp.plugin.diagram.IShapeTypeConstants
```

Имена свойств — константы `PROP_*` и `PROPERTY_*` в `com.vp.plugin.model.I*` и
`com.vp.plugin.diagram.shape.I*UIModel`. Наличие константы не гарантирует отрисовку: проверять
только экспортом картинки.

## 10. Запасной путь: плагин на Java (не требуется)

Помимо XML, Visual Paradigm позволяет строить модель программно через **Open API** — плагином
на Java. В Community Edition это разрешено, работает headless и проверено: собран плагин,
построивший диаграмму активности на девяти дорожках со всем нужным набором элементов.

Пользоваться им **не нужно**. Проверка раунд-трипом показала, что всё построенное плагином
выгружается в обычный `project.xml` и загружается обратно через `ImportXML` с идентичным
результатом. То есть Open API не даёт ничего сверх XML — ни автораскладки, ни недоступных
элементов, — но добавляет компиляцию, сборку jar и развёртывание в каталог плагинов.

Если путь всё же понадобится, ключевые факты: плагин реализует `VPPlugin` и
`VPPluginCommandLineSupport`, кладётся вместе с `plugin.xml` в
`%APPDATA%\VisualParadigm\plugins\<id>\`, запускается классом `com.vp.cmd.Plugin` с параметрами
`-project` и `-pluginid`. Компилировать с `--release 8`. Сам создать `.vpp` плагин не может —
пустой проект готовится заранее через `ImportXML`. И главное: только что созданная фигура
не имеет собранной подписи, поэтому перед заданием геометрии обязателен вызов
`setRequestResetCaption(true)`, иначе получится пустой прямоугольник без имени.

## 11. Технические мелочи окружения

- PowerShell помечает весь вывод `.bat` как ошибку (`NativeCommandError`) — это нормально,
  смотреть на фактический результат.
- Предупреждения `Ignoring option MaxPermSize`, `[Key-Mapping] Duplicated key id` и
  `illegal reflective access` безвредны.
- Самый первый в жизни запуск любой утилиты может напечатать `Feature not supported by current
  edition` до инициализации лицензионного состояния — повторить команду.
- Экспортированный PNG имеет альфа-канал: при обрезке через PIL сначала наложить на белый фон,
  иначе фрагмент выйдет чёрным.
- Большие XML с кириллицей не писать через bash-heredoc — ломается на кавычках; использовать
  запись файлом.

## 12. Чем версия в Visual Paradigm отличается от PlantUML

Содержание перенесено полностью: все узлы, связи, подписи, заметки и легенды на месте,
сверка велась поэлементно по каждой диаграмме. Отличается форма подачи — и почти всё
перечисленное ниже это ограничения формата, а не недоделки переноса.

### Теряется при переносе

| Что | Почему | Чем заменено |
|---|---|---|
| Заголовок диаграммы (`title`) | В Visual Paradigm нет свойства заголовка. Крупную надпись даёт только фигура `OpaqueAction` с полужирным шрифтом, оставляя лишнее действие в модели | Имя диаграммы, оно же имя PNG |
| Полужирный и моноширинный текст **внутри** заметок и легенд | Текст `NOTE` берётся только из `documentation` и рисуется одним начертанием | Текст перенесён дословно, выделение снято |
| Таблицы легенды с цветными ячейками | В заметке нет таблиц | Цвета названы словами: «серый — …», «сиреневый — …» |
| Пунктир у связи «по значению» (`..` между классами) | `<Line>` с `<Dashes>` разбирается, но на картинку не влияет — проверено замером пикселей | Сплошная линия, смысл несёт подпись и строка легенды |
| Заливка дорожек светло-серым | Залитый отсек закрывает стоящие в нём узлы, если не вкладывать каждый в `ChildShapes` | Дорожки белые, цветом выделена только внешняя система |
| Заголовки отсеков класса (`-- методы --`) | У отсеков в VP нет заголовков | Перенесены членами класса с неуказанной видимостью |
| Признак «интерфейс» | `modelType="Interface"` роняет импорт | Класс со стереотипом |
| Служебные связи `-[hidden]-` | Это подсказки раскладки Graphviz | Не нужны: раскладка задана координатами |

### Выглядит иначе

- **Подписи ветвлений в квадратных скобках** — `[да]`, `[нет — альт. поток 2а]`. Это запись VP
  для `guard`; текст совпадает с оригиналом дословно.
- **Крестик на дальнем конце направленной ассоциации.** Чтобы VP нарисовал одну стрелку, конец
  приходится пометить ненавигируемым, и на нём появляется крестик, которого в PlantUML нет.
  Без пометки связь считается двунаправленной и рисуется без стрелок вовсе.
- **Пустой отсек атрибутов** у класса без свойств: аналога `hide empty members` нет.
- **Переносы строк в подписях** местами сдвинуты, чтобы текст поместился в эллипс или ромб.
  Содержание сохранено, разбивка на строки — нет.
- **Габариты больше.** Диаграммы шире и выше PlantUML-рендера: раскладка задана вручную,
  а ветвления приходится разводить по отдельным колонкам, тогда как Graphviz уплотняет
  автоматически.

### Что лучше, чем в PlantUML

- Вопрос развилки рисуется **внутри ромба**, как и положено в UML, а не подписью рядом.
- Раскладка **детерминирована**: координаты заданы явно, и картинка не меняется от версии
  движка или набора шрифтов. PlantUML-рендер тех же исходников на другой машине даёт
  другие габариты.
- Результат — **настоящая модель UML**, а не только изображение: элементы живут в дереве
  проекта, их можно открыть в редакторе и править дальше.

### Чем это стоило

Автораскладки нет, поэтому каждая координата вычисляется вручную, а проверить результат можно
только отрисовкой. На диаграмму уходило от 3 до 9 итераций вида «поправить генератор → собрать
XML → импортировать → выгрузить PNG → посмотреть». В PlantUML этого цикла нет вообще: раскладку
считает движок, правится текст, результат виден сразу.

Поэтому исходники `.puml` стоит сохранить: они остаются быстрым способом менять содержание,
а генераторы в [`diagrams/vp`](diagrams/vp) переводят его в формат Visual Paradigm.

## 13. Конвертер: `.puml` → проект Visual Paradigm

Ручные генераторы `gen_*.py` писались по одной штуке на диаграмму, и дороже всего обходилась
раскладка — те самые 3–9 итераций. Конвертер убирает именно её.

### Откуда берутся координаты

Ключевая мысль: **раскладку не нужно придумывать — её уже посчитал PlantUML.** В `.puml`
координат нет, в XML Visual Paradigm они обязательны у каждой фигуры, но между ними есть
промежуточное звено — SVG, который PlantUML отрисовывает со всеми габаритами.

Конвейер:

```
.puml ──plantuml -tsvg──▶ .svg ──svgpos──▶ габариты ──puml2vp──▶ .xml ──ImportXML──▶ .vpp ──▶ .png
   │                                           ▲
   └──────── разбор смысла (кто есть кто) ─────┘
```

- [`svgpos.py`](diagrams/vp/svgpos.py) — снимает с SVG фигуры с текстом, свободные подписи,
  дорожки и рамки контейнеров. Тип диаграммы берётся из `data-diagram-type`.
- [`puml2vp.py`](diagrams/vp/puml2vp.py) — разбирает `.puml` по типам и собирает проект,
  подставляя снятые габариты. Запуск: `python puml2vp.py SM_UC2_UseCaseView` или `--all`.
- [`build.sh`](diagrams/vp/build.sh) — `XML → .vpp → PNG` с обязательной проверкой из §5.

Элементы `.puml` и фигуры SVG связываются **по тексту**: у узла в исходнике есть подпись,
у прямоугольника в SVG — она же. Сопоставление нормализует разметку (`**жирный**`, `<size:10>`,
`<<стереотип>>` → `«стереотип»`) и умеет искать по первой строке, по любой строке, по тексту
без строк-стереотипов и по началу текста — у состояний и объектов под именем бывает описание.

### Что из SVG брать нельзя

- **`data-source-line` не годится для привязки.** PlantUML ставит его только на заголовок
  и легенду: 2 вхождения на 21 узел. Сопоставление идёт по тексту, другого способа нет.
- **Маршруты связей не переносятся.** Узлы встают туда же, куда их поставил PlantUML,
  а линии между ними прокладывает сам Visual Paradigm.
- **Габариты пути нужно считать по командам.** У дуги `A rx ry rot flag flag x y` первые четыре
  числа — не координаты. Наивный поиск пар чисел превращает `A0,0 0 0 0` в точку (0,0)
  и растягивает заметку до начала холста.
- **Незалитая фигура — это линия,** а не прямоугольник: дуга перехода, рамка составного
  состояния, контур пакета. Её габариты случайно накрывают чужой текст, поэтому хранить
  в ней текст нельзя — иначе подписи переходов уезжают в соседнюю дугу.
- **Высокие фигуры не хозяева текста.** Фон дорожки и рамка `box` вокруг участников тянутся
  во всю высоту; оставь их — и они проглотят все подписи сообщений.
- **Текст заметок берётся из исходника,** а не из фигуры: контур заметки со сложенным углом
  часто накрывает стоящие рядом подписи связей, и в текст фигуры попадает чужое.
- **Строку собирают из нескольких `<text>`.** Как только в строке меняется начертание,
  PlantUML разбивает её на фрагменты — их нужно склеивать по общей базовой линии.

### Соответствие типов

| PlantUML | Диаграмма Visual Paradigm | Основные элементы |
|---|---|---|
| state machine | `StateDiagram` | `State2`, `InitialPseudoState`, `FinalState2`, `Transition2` |
| package | `PackageDiagram` | `Package`, `Component`, `Dependency` |
| deployment | `DeploymentDiagram` | `Node`, `Artifact`, `Association`, `Dependency` |
| sequence | `InteractionDiagram` | `InteractionActor`, `InteractionLifeLine`, `Message`, `CombinedFragment` |
| object + стрелки | `CommunicationDiagram` | `CommunicationLifeLine`, `InteractionLifeLineLink` |
| entity / class `<<table>>` | `ERDiagram` | `DBTable`, `DBColumn`, `DBForeignKey` |
| timing (`concise` / `robust`) | `TimingDiagram` | `TimingFrame`, `TimeUnit`, `LifeLine`, `StateCondition`, `TimeInstance` |

Составные состояния, пакеты и узлы переносятся с вложенностью: фигура кладётся в `ChildShapes`
родителя, модель — в его `ChildModels`. Про порядок наложения и момент заливки — см. §8.

### 13.1 Временная диаграмма

Самый неочевидный тип: у него **ровно одна фигура** — рамка `TimingFrame`, а всё содержание
лежит в дереве моделей. Поэтому три первых подхода и провалились — все они пытались выразить
состояния дочерними фигурами:

| Что пробовали | Результат |
|---|---|
| `StateInvariant` прямо в рамке | рамка и подписи линий жизни есть, отрезков нет |
| `StateInvariant` внутри `OCUnit` | то же; `OCUnit` рисуется сплошной полосой |
| строка состояния `OCUnit` + ломаная `OCLine` | импорт падает с `ClassCastException` |

Последнее объясняется просто: `IOCLineUIModel` наследует `IConnectorUIModel`, то есть `OCLine` —
связь, а не фигура. Ни `OCUnit`, ни `OCLine`, ни `StateInvariant` во временной диаграмме
вообще не участвуют.

**Строение.**

```
Model TimingFrame
├── ChildModels
│   ├── Model TimeUnit  name="0"   ← по одному на такт оси
│   ├── Model TimeUnit  name="50"
│   ├── Model LifeLine  name="Сервер"
│   │   └── ChildModels
│   │       ├── Model StateCondition name="нет связи"   ← строки состояний,
│   │       ├── Model StateCondition name="связь есть"     порядок = порядок строк
│   │       ├── Model DurationConstraint name="{≤ 60 с}"
│   │       │   └── ModelRefProperty startTime → TimeInstance
│   │       │       ModelRefProperty endTime   → TimeInstance
│   │       └── Model TimeInstance            ← момент: такт + состояние
│   │           └── ModelRefProperty timeUnit       → TimeUnit
│   │               ModelRefProperty stateCondition → StateCondition
│   └── Model TimeMessage name="…"  ← стрелка между линиями жизни,
│       startTime / endTime → TimeInstance
└── (фигура) Shape shapeType="TimingFrame" model="<id рамки>"
```

**Отрезок состояния — не объект.** Это серия подряд идущих `TimeInstance` с одной и той же
ссылкой на `StateCondition`. Границы отрезков включающие и перекрываются: на такте смены
состояния создаётся **два** момента на один и тот же `TimeUnit` с разными состояниями —
именно так рисуется ступенька перехода.

**Три вещи, без которых не работает:**

1. **`lifeLineWidth` и `1StCdW` в свойствах фигуры.** Это ширины колонок с именами линий
   жизни и с названиями состояний. По умолчанию они нулевые, и рамка не рисуется совсем —
   ни границы, ни содержимого. Третье свойство, `0vm`, — режим показа.
2. **Момент обязан ссылаться на состояние.** `TimeInstance` только с `timeUnit`, без
   `stateCondition`, не просто не рисуется — от него Visual Paradigm пропускает **всю рамку
   целиком**. Поэтому `{-}` из PlantUML («состояния нет») переносится не пустым моментом,
   а отсутствием моментов, а ограничение длительности, выходящее за пределы отрезка,
   подрезается до ближайшего такта с состоянием.
3. **Ширина такта задаётся в фигуре**, элементом `<TimeUnits><TimeUnit id width/></TimeUnits>`
   (и рядом `<Lifelines>` с высотами строк). Без него Visual Paradigm разносит такты поровну
   и ось перестаёт отражать длительности. Порядок детей `<Shape>` задан схемой:
   `DiagramElementProperties` → `Lifelines` → `TimeUnits` → … → `Caption` → `FillColor`.

**Рамке нужен `caption=False`** — иначе её имя рисуется второй раз по центру, поверх содержимого.

### 13.2 Как добывать строение, когда его негде подсмотреть

Приём, которым выяснено всё вышеописанное, годится для любого незнакомого типа диаграммы
и стоит дешевле перебора вслепую:

1. Найти официальный пример построения такой диаграммы через **Open API** (у Visual Paradigm
   они опубликованы по типам диаграмм).
2. Выполнить его **плагином в безголовом режиме** — обвязка описана в §10: `VPPlugin` +
   `VPPluginCommandLineSupport`, компиляция `--release 8`, запуск `com.vp.cmd.Plugin`.
   Открытие диаграммы в редакторе (`openDiagram`) убрать, проект сохранить.
3. Выгрузить полученный `.vpp` обратно: `ExportXML.bat -project … -out … -noimage`.
   Это и есть **эталон** — точные имена моделей, свойств и ссылок, порядок детей и реальные
   значения геометрии.
4. Проверить эталон обратным прогоном через `ImportXML` — убедиться, что он вообще
   импортируется, прежде чем сверять с ним свой файл.
5. Если свой файл всё равно не рисуется — **упрощать эталон в сторону своего**, а не наоборот:
   так за два-три прогона находится ровно то свойство или та связь, которой не хватает.

Именно шаг 5 и показал, что рамку убивает момент без состояния: эталон с урезанными
свойствами рисовался, а подстановка своих моделей — нет.

### Что не переносится

- **Заголовок диаграммы** — свойства заголовка в формате нет; ставится фигурой `TextBox`
  с текстом в атрибуте `name`. Модели с типом `TextBox` не существует, а текст из
  `documentation` эта фигура не показывает — в обоих случаях выходит пустая рамка.
- **Типы колонок на диаграммах БД.** `type` сверяется со справочником СУБД проекта,
  и всё незнакомое — `uuid`, `timestamptz`, `boolean` — молча становится `integer`.
  Свободное поле `typeName` на показ не влияет. Поэтому столбец типов гасится
  (`_showColumnTypes = false`), а тип пишется прямо в имя колонки: текст совпадает
  с исходником, и в модели не остаётся неверных значений.
- **Фигура `CommunicationMessage` через `ImportXML` не проходит** — импорт падает
  с `ClassCastException`. Сообщения переносятся подписью связи между линиями жизни;
  в исходнике на паре объектов и так ровно одна стрелка с нумерованным текстом.
- **Полосы активации** на диаграмме последовательности не переносятся.
- **Таблицы в легендах** — в заметке Visual Paradigm таблиц нет, разметка `|= … |` теряется.
- **Рамка `box` вокруг участников** диаграммы последовательности.
- **Подсветка интервала** (`highlight a to b #color`) на временной диаграмме — аналога нет.
- **Пропорции оси времени** переносятся шириной такта, но приблизительно: Visual Paradigm
  не делает ось непрерывной, он расставляет такты колонками заданной ширины.

### Проверка улучшений

Конвертер проверяется на тех же диаграммах, которые переводит: каждая правка прогоняется
через `puml2vp.py --all` и `build.sh`, после чего картинка смотрится глазами. Это остаётся
единственным надёжным критерием — см. §5.
