# Архитектурно значимые прецеденты — ИС «Караваны»

Документ содержит детальное описание прецедентов, оказывающих ключевое влияние на архитектурные решения: интеграции с внешними системами, офлайн-синхронизация, мультитенантность, state machine статусов рейса, обработка инцидентов.

Полный список прецедентов см. в [UseCases.md](UseCases.md).

| # | Прецедент | Архитектурный аспект |
|---|-----------|----------------------|
| UC-1  | Создать заявку на перевозку                    | Ядро системы: связывает маршрут, risk_score, команду, груз, интеграция с Wasteland Intel |
| UC-7  | Рассчитать risk_score                          | Интеграция с внешней системой, обработка недоступности и устаревших данных |
| UC-16 | Подтвердить ключевые этапы рейса               | Офлайн-синхронизация Pip-Boy, state machine статусов, CheckpointLog |
| UC-19 | Зафиксировать инцидент                         | Офлайн-фиксация, 3 актора, автопереход статуса, триггер RecoveryRequest |
| UC-32 | Создать организацию                            | Мультитенантность, изоляция данных, создание диспетчера в рамках организации |

## UC-1. Создать заявку на перевозку

| Прецедент: Создать заявку на перевозку |
|:---|
| **ID:** UC-1 |
| **Краткое описание:** Диспетчер создаёт новую заявку на перевозку, выбирая шаблон маршрута или заполняя данные вручную. |
| **Главные актёры:** Диспетчер караванов |
| **Второстепенные актёры:** Wasteland Intel (для расчёта risk_score) |
| **Предусловия:**<br>1. Диспетчер аутентифицирован в системе.<br>2. В системе существует хотя бы один маршрут (шаблон) или диспетчер готов задать маршрут вручную. |
| **Основной поток:**<br>1. Диспетчер открывает форму создания заявки.<br>2. Диспетчер заполняет основные данные: пункт отправления, пункт назначения, желаемая дата отправки, описание груза.<br>3. Диспетчер выбирает маршрут из списка шаблонов.<br>4. Система запрашивает данные об угрозах из Wasteland Intel и рассчитывает risk_score маршрута.<br>5. Система рассчитывает ETA на основе маршрута и текущей обстановки.<br>6. Диспетчер указывает оценочную ценность груза (в крышках).<br>7. Система пересчитывает risk_score с учётом ценности груза и формирует рекомендацию по минимальному составу охраны и объёму припасов.<br>8. Диспетчер проверяет сводку заявки и подтверждает создание.<br>9. Система сохраняет заявку со статусом Draft и записывает событие создания в журнал аудита. |
| **Постусловия:**<br>1. В системе создана заявка со статусом Draft.<br>2. Заявка содержит маршрут, ETA, risk_score и рекомендацию по охране/припасам.<br>3. В журнале аудита зафиксировано событие создания заявки. |
| **Альтернативные потоки:**<br>3а. Диспетчер формирует маршрут вручную (задаёт контрольные точки) вместо выбора шаблона → поток продолжается с шага 4.<br>4а. Wasteland Intel недоступен — система создаёт заявку без risk_score, помечает поле как «Требует пересчёта» и уведомляет диспетчера.<br>8а. Диспетчер отменяет создание — заявка не сохраняется. |
| **Включаемые прецеденты:**<br>UC-5 «Выбрать/спланировать маршрут», UC-6 «Рассчитать ETA», UC-7 «Рассчитать risk_score», UC-8 «Получить рекомендацию по охране и припасам», UC-12 «Указать ценность груза». |

## UC-7. Рассчитать risk_scoreпо п

| Прецедент: Рассчитать risk_score |
|:---|
| **ID:** UC-7 |
| **Краткое описание:** Система автоматически рассчитывает оценку риска маршрута на основе данных Wasteland Intel и ценности груза. |
| **Главные актёры:** Диспетчер караванов |
| **Второстепенные актёры:** Wasteland Intel |
| **Предусловия:**<br>1. Для заявки выбран или сформирован маршрут (UC-5).<br>2. Указана ценность груза (или используется значение по умолчанию). |
| **Основной поток:**<br>1. Система формирует запрос к API Wasteland Intel, передавая список контрольных точек маршрута.<br>2. Wasteland Intel возвращает данные об угрозах по каждому участку маршрута (тип угрозы, уровень опасности, дата актуальности).<br>3. Система агрегирует данные об угрозах и вычисляет базовый risk_score маршрута.<br>4. Система применяет корректирующий коэффициент ценности груза: чем выше ценность, тем выше итоговый risk_score.<br>5. Система сохраняет итоговый risk_score в заявке и отображает его диспетчеру.<br>6. На основе risk_score система автоматически формирует рекомендацию по минимальному составу охраны и объёму припасов (UC-8). |
| **Постусловия:**<br>1. Заявка содержит актуальный risk_score.<br>2. Сформирована рекомендация по охране и припасам. |
| **Альтернативные потоки:**<br>2а. Wasteland Intel недоступен или возвращает ошибку — система устанавливает risk_score = «Н/Д», помечает заявку как «risk_score требует пересчёта» и уведомляет диспетчера. Диспетчер может повторить расчёт позднее.<br>2б. Wasteland Intel возвращает данные с датой актуальности старше 24 часов — система рассчитывает risk_score, но помечает его как «На основе устаревших данных» и предупреждает диспетчера. |

## UC-16. Подтвердить ключевые этапы рейса

| Прецедент: Подтвердить ключевые этапы рейса |
|:---|
| **ID:** UC-16 |
| **Краткое описание:** Караван-мастер подтверждает ключевые этапы: загрузка, выход, прибытие на контрольные точки, доставка груза. |
| **Главные актёры:** Караван-мастер |
| **Второстепенные актёры:** Нет |
| **Предусловия:**<br>1. Караван-мастер аутентифицирован и назначен на рейс.<br>2. Рейс находится в статусе Ready или En Route. |
| **Основной поток:**<br>1. Караван-мастер открывает карточку рейса на Pip-Boy.<br>2. Система отображает текущий этап рейса и список предстоящих этапов.<br>3. Караван-мастер выбирает действие «Подтвердить этап» для текущего этапа (загрузка завершена / караван вышел / прибытие на контрольную точку / груз доставлен).<br>4. Система автоматически фиксирует временную метку и координаты.<br>5. Система выполняет переход статуса рейса согласно статусной модели (например, Ready → En Route при подтверждении выхода).<br>6. Система сохраняет запись в CheckpointLog.<br>7. Если есть связь с сервером — данные синхронизируются немедленно. |
| **Постусловия:**<br>1. Этап рейса зафиксирован с временной меткой и координатами.<br>2. Статус рейса обновлён в соответствии со статусной моделью.<br>3. Запись добавлена в CheckpointLog. |
| **Альтернативные потоки:**<br>7а. Связь с сервером отсутствует — данные сохраняются локально на Pip-Boy и автоматически синхронизируются при восстановлении соединения. При синхронизации сервер проверяет временные метки и применяет события в хронологическом порядке.<br>5а. Караван-мастер пытается подтвердить этап вне допустимого порядка (например, «доставлен» без «вышел») — система отклоняет действие и отображает сообщение о необходимости подтвердить предыдущий этап. |
| **Точки расширения:**<br>EP-1 «Прибытие на контрольную точку» (шаг 3, этап «прибытие на КТ») — расширяется UC-17 «Отметить прохождение контрольной точки».<br>EP-2 «Прохождение КПП» (шаг 3, этап «прибытие на КПП») — расширяется UC-18 «Отметить прохождение КПП (с пошлиной)».<br>EP-3 «Подтверждение доставки» (шаг 3, этап «груз доставлен») — расширяется UC-14 «Подтвердить доставку груза (с пломбой)». |

## UC-19. Зафиксировать инцидент

| Прецедент: Зафиксировать инцидент |
|:---|
| **ID:** UC-19 |
| **Краткое описание:** Полевой пользователь фиксирует инцидент через форму: тип, тяжесть, описание; время и координаты фиксируются автоматически. |
| **Главные актёры:** Караван-мастер, Капитан охраны, Полевой медик |
| **Второстепенные актёры:** Нет |
| **Предусловия:**<br>1. Пользователь аутентифицирован и назначен на рейс.<br>2. Рейс находится в статусе En Route или Delayed. |
| **Основной поток:**<br>1. Полевой пользователь открывает форму фиксации инцидента на Pip-Boy.<br>2. Система автоматически заполняет временную метку и координаты на основе данных устройства.<br>3. Пользователь выбирает тип инцидента из предопределённого списка (нападение, поломка, медицинское происшествие, потеря груза, стихийное бедствие, прочее).<br>4. Пользователь указывает тяжесть инцидента (низкая, средняя, высокая, критическая).<br>5. Пользователь вводит текстовое описание и при необходимости указывает пострадавших участников команды.<br>6. Пользователь подтверждает отправку.<br>7. Система сохраняет карточку инцидента и привязывает её к текущему рейсу.<br>8. Если тяжесть «высокая» или «критическая» — система автоматически переводит рейс в статус Delayed.<br>9. Если есть связь — данные синхронизируются с сервером и диспетчер получает уведомление. |
| **Постусловия:**<br>1. Карточка инцидента создана и привязана к рейсу.<br>2. При высокой/критической тяжести статус рейса изменён на Delayed.<br>3. Диспетчер уведомлён об инциденте (при наличии связи). |
| **Альтернативные потоки:**<br>9а. Связь отсутствует — карточка инцидента сохраняется локально на Pip-Boy и синхронизируется при восстановлении соединения; при синхронизации диспетчер получает уведомление с фактическим временем инцидента.<br>6а. Пользователь отменяет заполнение — карточка не сохраняется. |
| **Точки расширения:**<br>EP-1 «Критический инцидент зарегистрирован» (после шага 8, при тяжести «высокая» или «критическая») — расширяется UC-20 «Инициировать RecoveryRequest» (эвакуация, подмога, повторная доставка). |

## UC-32. Создать организацию

| Прецедент: Создать организацию |
|:---|
| **ID:** UC-32 |
| **Краткое описание:** Суперпользователь создаёт новую организацию (караванную компанию) в системе. |
| **Главные актёры:** Суперпользователь |
| **Второстепенные актёры:** Нет |
| **Предусловия:**<br>1. Суперпользователь аутентифицирован в системе. |
| **Основной поток:**<br>1. Суперпользователь открывает административный интерфейс управления организациями.<br>2. Суперпользователь выбирает действие «Создать организацию».<br>3. Суперпользователь заполняет данные организации: название, уровень подписки, контактные данные.<br>4. Система проверяет уникальность названия организации.<br>5. Система создаёт организацию и выделяет для неё изолированное пространство данных (все сущности организации привязываются к её идентификатору).<br>6. Система предлагает назначить первого диспетчера организации (UC-33).<br>7. Суперпользователь вводит ФИО, логин и начальный пароль для первого диспетчера.<br>8. Система создаёт учётную запись диспетчера, привязанную к новой организации.<br>9. Система записывает событие создания организации и назначения диспетчера в журнал аудита. |
| **Постусловия:**<br>1. В системе создана новая организация с изолированным пространством данных.<br>2. Создана учётная запись первого диспетчера, привязанная к организации.<br>3. Организация активна и готова к использованию.<br>4. В журнале аудита зафиксированы события создания. |
| **Альтернативные потоки:**<br>4а. Название организации не уникально — система отображает ошибку, суперпользователь вводит другое название.<br>6а. Суперпользователь пропускает назначение диспетчера — организация создаётся без пользователей, диспетчера можно назначить позже через UC-33. |
| **Точки расширения:**<br>EP-1 «Организация создана» (шаг 6, опционально) — расширяется UC-33 «Назначить первого диспетчера организации».<br>EP-2 «Организация создана» (после шага 9) — расширяется UC-34 «Управлять подписками» (активация подписки выбранного уровня). |
